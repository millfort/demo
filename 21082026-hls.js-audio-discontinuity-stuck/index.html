The gate that decides everything

—
doTickIdle() in audio-stream-controller returns on its very first line, if (bufferLen >= maxBufLen …) return;. bufferLen is measured not from the playhead but from getLoadPosition() — which, after the race, keeps returning the frozen nextLoadPosition. The position never moves, so the "buffer is full" verdict never changes.

What this page adds on top of a plain player

Inside hls.js — nothing. It is stock hls.js@1.6.16 from the CDN. Exactly four things are added, and all four are marked in the source of this page with a // [PATCH N] comment:

  1. A logger. debug: {log, warn, …} in the config, so that hls.js lines end up on screen. Does not affect behaviour.
  2. A start position. Seek to discontinuity − maxBufferLength − 10, so the player reaches the discontinuity with a saturated buffer. This is mandatory: seek right next to the discontinuity and the buffer is empty, and the bug will not happen.
  3. A delay on the video init segment in the loader — purely so you do not have to win a 3-millisecond lottery. Only the request with frag.sn === 'initSegment', frag.type === 'main' and frag.cc > 0 is held back. The checkbox turns it off.
  4. An in-memory loader. The test stream lives in stream-data.js as base64; the loader hands those bytes to hls.js instead of doing an XHR, which is what lets this page run straight off the filesystem. It is a byte source and nothing else — no timing, buffering or scheduling logic is touched. Type any real HLS URL into the Source field and the very same loader falls through to the stock XHR loader.
Why delaying a video media segment gets you nowhere 
// base-stream-controller.ts, _doFragLoad()
result = this.fragmentLoader.load(frag, ...);                       // your loader is called here
this.hls.trigger(Events.FRAG_LOADING, { frag, targetBufferTime });  // and this fires immediately

FRAG_LOADING sets mainFragLoading = {cc: 1} synchronously, before your async delay ever runs. And the guard in syncWithAnchor looks at exactly that mainFragLoading.cc:

if (mainFragLoading?.cc === waitingToAppend.cc) return;   // 1 === 1 -> just keep waiting

So delaying a media segment does not open the window, it slams it shut. Init segments never reach mainFragLoading at all:

if (!this.audioOnly && data.frag.type === MAIN && isMediaFragment(data.frag)) {
  this.mainFragLoading = data;      // NOT executed for sn === 'initSegment'
}

Hence the window = the time it takes to load the video init segment at the discontinuity.

What the "Revive audio" button does 
const asc = hls.audioStreamController;
asc.fragmentTracker.removeFragmentsInRange(0, Infinity, 'audio', false, true); // clear APPENDING
asc.startLoad(video.currentTime);                                  // unfreeze nextLoadPosition

A plain hls.stopLoad()/startLoad() is not enough: it only cleans the tracker if fragCurrent still has a live loader, and by that point it has been released.

How the test stream was made

make-stream.sh next to this file, ffmpeg only. Two independently encoded parts — 48 s of testsrc2 + a 440 Hz pulsing tone, then 40 s of smptebars + 660 Hz — cut into 4-second fMP4 segments and glued together with an EXT-X-DISCONTINUITY. Part B carries its own EXT-X-MAP, which is what forces hls.js to fetch a video init segment at cc > 0: that fetch is the race window. Audio and video are separate renditions, so audio has its own stream controller — without that split there is no bug to have.
